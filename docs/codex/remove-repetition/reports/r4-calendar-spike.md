Measured and confirmed in installed source: the cutoff is **container width < 43.75 rem**, or <700 px here, not window width. **There is no built-in 520 px cutoff.** Exactly 700 px is wide. The fallback chooses the first compatible configured view; view order matters.

However, the library remeasures on mount and **window `resize` only**, not with ResizeObserver. Resizing the container from 1000 to 420 px while keeping the window at 1440 left month-grid and `isSmall:false`; changing the window to 1439 px then switched to month-agenda and `isSmall:true`. `controls.setView('month-grid')` can still force a narrow grid programmatically. With `isResponsive:false`, the picker retains wide-view filtering at every width; it does not automatically offer agenda. The plan needs its own container observer/view policy, including picker behavior. Installed-source excerpts and all raw snapshots are linked in the evidence.

## 6. Rendering and “+N more”

The Monday–Friday sample uses **inclusive** PlainDate endpoints `2026-10-19` through `2026-10-23`.

- **Month grid:** one horizontal band across five cells, Monday through Friday, with width `calc(500% - 5px)` (about 703.5 px in the 1000 px calendar). It does not extend into Saturday. The title `Quiz week · Quiz 2 · date depends on your lab section` remains readable in this band. Grid events use `white-space:nowrap; overflow:hidden`; a long title in a single cell, such as the timed second-hour example, is visibly clipped. Merely putting important qualifiers in the title does not guarantee every qualifier stays visible in the grid.
- **Month-agenda:** date dots mark the covered days. Selecting each day Monday–Friday shows the same event as an agenda card with its full title and `October 19, 2026 – October 23, 2026`; Saturday shows “No events.” This is a selected-day list under a month date picker, not a five-day horizontal band or a continuous month list. At a 390 px viewport / 360 px container the qualifier is readable, with `white-space:normal` and no title overflow (322 px client/scroll width). This is the default theme at the site's current typography, not a test of the future C1 sizes.
- **Busy day:** the five same-day events overlap the week-span event, making six events on October 22. The default four slots show the span, three busy events, then **“+ 2 events”**. Clicking it changes to **day** view for October 22 after the built-in delay. It does not open an overflow popover.
- **Override:** `callbacks.onClickPlusEvents(date, event)` replaces that behavior. The probe recorded date `2026-10-22` and stayed in month-grid. `monthGridOptions.nEventsPerDay` controls the slot count (default 4). Without a configured day view, the default plus action has no day view to select, so the integration must configure one or override it.

## 9. Accordion, browser find and no JavaScript

Measured with Chromium **154.0.8037.57** and Playwright WebKit **26.5**: [accordion evidence](r4-evidence/accordion.json). Both engines completed all three probe modes with zero page errors. All three panels are present in exported HTML using `forceMount`; Radix itself does not apply `display:none` to force-mounted content. Its content props permit a native hidden attribute.

Two surrounding integration problems matter:

1. React **18.2** treats JSX `hidden="until-found"` as a boolean attribute and emits **`hidden=""`**. Native `setAttribute('hidden','until-found')` preserves the token. The literal JSX mode confirms the problem.
2. The site's `all:unset` reset overrides the native hiding behavior: raw hidden panels can remain visible. The corrected probe explicitly applies `content-visibility:hidden` to `[hidden=until-found]`. Its default progressive mode also uses the existing pre-paint `.js` marker to hide closed panels before hydration, and synchronously opens a match in its native `beforematch` handler.

| Actual reveal operation | Chromium | Playwright WebKit |
| --- | --- | --- |
| Native text-fragment link, corrected `until-found` mode (attribute-only hiding after hydration) | Trusted `beforematch` **1**, panel opens | Trusted `beforematch` **1**, panel opens |
| Native text-fragment link, default progressive `no-js-safe` mode | **0**, panel stays closed | Trusted `beforematch` **1**, panel opens |
| Actual browser Ctrl+F, default progressive mode | **0**, panel stays closed | Browser chrome find not automated |

All query modes share the exported `no-js-safe` default until the parent effect applies query settings. The positive `until-found` result describes its attribute-only hiding after hydration, not a separately exported first-paint sequence.

Chromium Ctrl+F used a headed browser under Xvfb and actual X11 keyboard input (`xdotool`), searching for `R4PANELBRAVO`: [native find evidence](r4-evidence/native-find.json). No test dispatched a fake `beforematch`. Isolated native controls distinguish the failure: a token present in the initial parsed HTML reveals successfully; a dynamically added token after pre-paint `content-visibility:hidden` reproduces the failure. Thus `forceMount` support and browser support for the event do **not** establish that the proposed React 18 progressive path works. This remains an integration blocker.

`window.find` was tested separately and is not equated with Ctrl+F: it never fired `beforematch`; WebKit can return true without selecting/revealing the closed text. Expand all and Collapse all work for all three panels in both engines. A browser without usable reveal behavior needs Expand all; this fallback is also needed for the failing Chromium path until addressed.

**No JavaScript:** the exported default progressive mode has no hidden attribute, all content is force-mounted, and only `.js`-scoped rules hide closed panels. With JavaScript disabled, `.js` is absent, and all three explanations have visible content, nonzero text height and `content-visibility:visible` in both engines. This approach preserves no-JS reading, even though its Chromium find behavior needs revision. An unconditional hidden attribute or unconditional closed-state hiding would not provide that fallback.

**Playwright WebKit is not the same as iPhone Safari.** Neither its text-fragment result nor Chromium's Ctrl+F result settles Safari's actual find UI or iOS behavior; those remain real-device checks.

## 10. Calendar loading failure

No uncaught page error occurred: [calendar evidence](r4-evidence/calendar.json), [failure screenshot](r4-evidence/calendar-failure-1440.png).

The boundary alone is not sufficient for this `next/dynamic` loader: its `loading({error})` component explicitly rethrows a rejected import to reach the boundary. There is no calendar-wide failure fallback without handling that path. No real assignment list was built; this tests isolation with static sample dates and independent controls.

### Blockers and owner follow-up

- **C5's combination of first-paint hiding and Chromium find-in-page is not working in the measured React 18 path.** Resolve and remeasure the serialized-token/progressive approach before claiming closed panels are searchable. Radix itself and native `beforematch` do work in the positive controls.
- **C4 cannot rely on built-in container observation or a 520 px breakpoint.** Add and test the planned ResizeObserver/view policy; the built-in cutoff is 43.75 rem and is only reevaluated on window resize.
- **Default grid clipping can hide qualifiers**, particularly the timed single-cell title. Preserve full wording in the assignment view and validate the final event rendering at C1 typography sizes.
- **Real iPhone/iPad and Safari find/touch checks are still outstanding.** Emulated touch and Playwright WebKit do not close those questions. The spike does not implement or test the real pinned assignment window, steering, section changes or production styling.
- The root suite has the documented baseline failure. There is **no measured licence, React-peer, lint/build, CSP, remote-request or chunk-failure-isolation blocker** for the chosen package versions.

### Reproducing the measurements

Build with `npm ci`, `npm test`, `npm run build` from `site/`. Serve only `site/out` using `node scripts/spike-server.mjs` (default port 4174). The HTML retains the real CSP. Probe query parameters: `width`, `responsive`, `view`, `more=override`, `accordion=naive|until-found|no-js-safe`, `prevent=false`; use `motion=off` to settle the existing shell.

From `site/`, with externally installed Playwright:

```sh
node scripts/spike-package-measurements.mjs
node scripts/spike-bundle-measurements.mjs
PLAYWRIGHT_PATH=/path/to/node_modules/playwright QA_CHROMIUM_PATH=/path/to/chromium node scripts/spike-calendar-measurements.mjs
PLAYWRIGHT_PATH=/path/to/node_modules/playwright/index.mjs CHROMIUM_PATH=/path/to/chromium node scripts/spike-accordion-measurements.mjs http://127.0.0.1:4174/tmu-course-guides/next/spike/
DISPLAY=:92 PLAYWRIGHT_PATH=/path/to/node_modules/playwright XDOTOOL_PATH=/path/to/xdotool node scripts/spike-native-find-measurements.mjs
```

Calendar QA starts its own static server; accordion/native-find QA use the running server. WebKit must be installed for that Playwright version with its host libraries available. The headed native-find script also requires Xvfb or a real X display and xdotool. These are QA dependencies, not additions to the application.
